# Метод sdd-visualizer

Метод spec-driven development для приложения на **React**, **Nest SSR** и **PostgreSQL**. Визуализатор этого репозитория лежит в `apps/web` и `apps/server` и базу не использует. Спецификации продуктов живут в `docs/<проект>/<фича>/`.

Подход фиксирует поведение спецификацией до кода. Реализация, тесты и ревью сверяются с этой спецификацией.

Метод описан в терминах приложения: страница React (`apps/web/src/pages`), сценарий экрана (`apps/web/src/features`), общий код (`apps/web/src/shared`), Nest-модуль и SSR (`apps/server/src/<feature>`, `apps/server/src/ssr`), сущности и миграции TypeORM (`apps/server/src/database`), эталоны каталогов и постоянные правила.

Правила агентов в `.cursor/rules/` задают, как планировать работу и проверять результат; сам метод описан документами ниже.

## Где живёт спецификация

Спецификация фичи лежит в `docs/<проект>/<фича>/`. Файл роли лежит в `in-progress`, `ready-to-implement` или `done`.

| Роль | Файл |
|------|------|
| Аналитик | `analyst.md` |
| Дизайнер | `designer.md` |
| Backend | `backend.md` |
| Тестировщик | `tester.yaml` |
| Frontend | `frontend.md` |

Вид каждого файла и критерии `AN-*`, `DS-*`, `BE-*`, `QA-*`, `FE-*` — в [05-docs-repo.md](./05-docs-repo.md). Критерии поведения фичи `AC-*` выпускает только аналитик. Постоянные правила слоёв и эталоны остаются в репозитории приложения.

Правила и эталоны задают, как писать код. Спецификация задачи задаёт, что должно получиться и как это проверить.
